0. GIVEN
  G1 No give-back: Candidates and BufferBytes never decrease. A declined read (ErrIndexNotFound) keeps what its
     shards walked; the fallback is new work. G2 Pruned and dropped entries are charged (design-fixround.txt 1).
  From G1 one fact carries this design: every meter counter is monotone, so the candidate room only shrinks.
  "n > room" seen once stays true, and an add made after that comparison always passes the limit.

1. STAGED IS DELETED. SHARDS CHARGE THE METER DIRECTLY.
  A stage had three jobs. (a) hold charges back so that a decline costs nothing: withdrawn by G1. (b) one allowance
  over the shards: the meter's atomic counters give that, live, to every tally on it. (c) one kept error so that the
  other shards stop: ReadMeter.exceeded keeps the first refusal, tiered's workers check it before each shard, and a
  shard that charges the same counter after the refusal is refused by its own add. Nothing is left for a stage.
  Removed from pkg/graph/store/read_budget.go: Staged, tallyStage (charge, refuse, flush, commit), bufferRoom, the
  ReadTally.stage field and its branches in Candidates, Buffer and CandidatesAhead, the synthetic "room did not
  move" error. f578c970's release, giveBack, ahead and addCandidatesAhead are never brought in.
  Callers of Staged() (grep -rn 'Staged()' pkg/ at 48d6c5a4), all of them:
    tiered/tieredstore_tx_members.go:540 propertyTxMemberAnswers -> each(bs, opens, ...) and
        opens.Buffer(shardMemberBytes); commit() and its error return go; the two decline returns stay plain
        returns; the comment at :509-520 rewritten to what the code does.
    store/read_budget_test.go:166-250 TestReadTally_Staged -> deleted; cumulative, nested and nil cases move to H1.
    tiered/tieredstore_tx_members_decline_test.go TestTieredMemberDeclineCostsNothing (the withdrawn contract) -> D1.
  Finding 6 (two mutex takes a member): atomics suffice. A member's charge is ReadMeter.add, one atomic add a meter
  of the chain, as on every unstaged tally today. The one mutex left is the hold scope's (section 2), taken once a
  set (Hold) and once a Drop call, never on the per-member path.

2. THE PRIMITIVE: THE ROOM NET OF THE READ'S HOLDS, AND ONE ADMISSION AGAINST IT
  type holdScope struct { mu sync.Mutex; pending atomic.Uint64; err error }   // one a read; pending written under mu
  ReadTally gains `hold *holdScope` (in place of `stage`). File read_budget.go; gather_hold.go deleted (lane A).
    func (t *ReadTally) Held() *ReadTally   // t with a scope; nil t, no candidate limit on the chain, or t already
                                            // scoped: t itself (one scope a read; shards and labels share it)
    func (t *ReadTally) CandidateRoom() uint64       // min over the chain of (bound - candidates), read live, minus
                                                     // the scope's pending, floored at 0; MaxUint64 without a limit
    func (t *ReadTally) Hold(n int) error            // ahead(n, keep)
    func (t *ReadTally) CandidatesAhead(n int) error // ahead(n, do not keep): the same admission, nothing retained
    func (t *ReadTally) Drop(n int) error            // n held entries are counted now
  Every reader of the room (listCap, membersFit, TrackUnder, the stores) gets that figure; nobody keeps it across work.
  ahead(n, keep), the one admission (owner: the meter):
    scoped, under mu: kept err -> return it; meter.Exceeded() -> return it (another limit stopped the read).
      n <= CandidateRoom(): keep -> pending += n; return nil.
      else: total := pending + n; pending = 0; err = meter.AddCandidates(door, total); scope.err = err; return err.
    unscoped: Hold returns nil and holds nothing (gatherFree, design-fixround O3). CandidatesAhead: n <= room -> nil,
      else return meter.AddCandidates(door, n).
    The refusal is decided by the comparison and made by one add that is kept (the entries held are work the read
    needed; documented since R2 late counts). By monotonicity that add passes the limit of the meter whose room was
    the minimum, so it never returns nil: there is no path "compared over, added, came back nil, bounds nothing".
  Drop(n), scoped, under mu: kept err -> return it and count nothing (the refusal counted them). pending -= min(n,
    pending); err = meter.AddCandidates(door, n); a refusal is kept. Unscoped: Candidates(n).
    Under one mutex pending and the meter move together, so the room is unchanged by a Drop: no Hold sees the
    entries in both places (a false refusal) or in neither (a hold past the room).
  Who settles a held entry (the rule builders must keep):
    - dropped by a filter (pin, After, envelope prune, a second shard's or label's duplicate): the dropper, Drop.
    - read by the helper that held it: that helper, Drop(1) in place of Candidates(1).
    - handed on to a door that counts it with its own Candidates: it stays pending until the read ends (the scope
      dies with the read). So within one read every Hold precedes the door's first read of a handed-on entry. Lane A
      keeps this: the gathers (all labels, all shards) finish before the scan reads. A Hold after such reads counts
      those entries twice: high, never low, but it breaks invariant I, so no new caller may do it; a fan-out whose
      shards hold and read in parallel must settle with Drop.
  A hold lasts one read. Charges are shared live by every read on a meter; holds are not: R concurrent reads on one
  context may each hold up to the room, so the copies made ahead are bounded by R x room, while the count itself
  never passes the limit (the door's charge refuses at the entry past it). A meter-wide pending would need a release
  when a read ends early (Limit, fn false): a give-back with a lifetime, which G1 removes. Documented (O7), not built.

3. THE REVIEW'S SIX FINDINGS
  1 release un-spends the meter: gone. No function subtracts from a counter; the only decrement is
    holdScope.pending, which is not Work. P1 samples Work during the run and asserts it never falls.
  2 GatherHold's refuse returning nil and spending its once: GatherHold is deleted; Hold has no once and no second
    evaluation (comparison, one add, kept error). H1: every Hold past the room, and every Hold after it, errors.
  3 snapshot rooms. Hold reads the room under the scope's mutex as it admits. TrackUnder
    (pkg/graph/internal/index/valid_end.go:169-185), signature unchanged so that lane B's files are not touched:
        skip the count when t.CandidateRoom() == math.MaxUint64 (no limit exists; not a room kept for later); else
        n := len(ix.unknown); for each member not yet unknown: n++; if err := t.CandidatesAhead(n); err != nil
            { return false, err }
    One call a new entity (atomic loads); the room is read at every step. The refusal counts n, as today.
    ResolveUnknownUnder / ResolveUnknownBulkUnder keep CandidatesAhead(len(ix.unknown)).
    Why not Hold here: the unknown entities are counted by the stores' row readers (badgerstore_valid_end.go:180,
    :335, :368; memorystore_valid_end.go:119), and TrackUnder and Resolve look at the same entities; a retained hold
    counts them twice unless those readers settle with Drop, and they are in lane B's file. Open as O6.
  4 the transient add: addCandidatesAhead never exists. Within the room nothing is added, so nothing is subtracted
    and no other charge can see a count that is not real. Past the room the add is kept.
  5 ReadBudgetError.Work, replacing "Work is that budget's meter" (read_budget.go:74-76) and api.md: Work is the
    meter's counters as the charge that passed the limit read them, right after its own add. Work.<Limit> is above
    Budget.<Limit>; every field is at most meter.Work() read after the door returned. They are equal only when one
    goroutine charges the meter and nothing is charged after the refusal. On tiered each parallel shard may make
    its own refusal; allShardsBut joins them (errors.Join, tieredstore_tx_members.go:81): errors.As gives the first
    in shard order, meter.Exceeded() the first in time. Tests compare with meter.Work() by <=, by == only where
    one goroutine charges.   Finding 6: section 1.

4. LANE A ON THIS PRIMITIVE (design-fixround.txt sections 2, 3, 5 stand, with these changes)
  - "Staged() copies the scope pointer" and "stage.refuse on a staged tally" are void: no stage.
  - "CandidatesAhead stays as it is" becomes: ahead(n, do not keep), net of the read's holds; its refusal on a
    scoped tally counts the pending entries too (they are cleared, so nothing counts twice).
  - Hold checks meter.Exceeded first, so a shard does not copy a set after another limit stopped the read.

6. COUNTS THAT CHANGE FOR SIGMA AND AI-SOC (on top of design-fixround.txt 3.3, 4, 5)
  C1 A tiered property membership read that declines (a shard without the index or still building it; node Keys and
     rel type doors, TxPin and window) keeps the Candidates its shards examined and the BufferBytes of the lists
     they kept (16 a member); the graph's fallback counts on top. It cost only the fallback.
  C2 So a budget that answered through the fallback can now refuse. The budget that answers is the unlimited
     control's Work, declines included (invariant I extended to a decline).
  C3 meter.Work() during a fan-out includes what the shards charged so far (it appeared at commit). A second read on
     the same context is refused as soon as both together pass the limit.
  C4 A refusal is always the meter's own typed error from the charge that passed; under parallel shards the door
     returns a join of them and Work follows section 3 finding 5 (it is not always the final meter.Work()).
  C5 CandidateRoom is net of holds: a listing capped by listCap after a hold lists fewer.
  C6 A valid-end first call is refused when other charges on the context shrink the room during the enlistment walk.
  C7 Unchanged: ShardOpens, DecodedBytes, HistoryExamined; answered reads with no decline or drop; unbudgeted reads.

10. RISKS
  1 C1 / C2: a decline costs up to the value on every indexed shard, then the fallback. Stores with a shard still
    building pay both until it is built; consumer budgets sized on the fallback refuse. O8 is the mitigation.
  2 The "Hold before the door reads" rule of section 2 is kept by code order, not by the type. T6 (the control's
    count answers as the budget) on four backends is what catches a builder who breaks it.
  3 Refusal Work under parallel shards is a snapshot (finding 5): consumer tests that compare it with meter.Work()
    by equality on tiered must move to <=.
  4 TrackUnder calls CandidatesAhead once a new entity under ix.mu (atomic loads within the room): not measured.
    P1 and H1's concurrent part are schedule tests (200 rounds, -race by hand); the others are deterministic.
  5 O6 and O7 are stated limits, not fixes: api.md must list them, or its table claims a bound the code lacks.
