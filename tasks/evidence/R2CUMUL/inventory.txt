R2-6 INVENTORY: native work on the budgeted read paths that is not charged before it is done (14 Nov, worktree
branch at 8d99c2e5 = R2-1 GATHERHOLD + R2-2 VEATTRIB; R2-3, R2-4, R2-5 in progress on their own branches).

Method. A scan of every non-test function in pkg/graph/store/** that takes a *ReadTally or *GatherHold and does
native work (an iterator, a write-buffer range, a slice or map built, a decode, a shard open, a history fold) with
no charge call in its own body: 42 functions. Each was read: most hand the tally to the callee that charges
(checkout*Charged, forEach*ShardCharged, the metered read snapshot, mintLegIDsTallied, relationshipRowVia); those
are charged where the work is done and are not listed. What remains, each with the reason and the owner:

A. Not charged, open (each a work item or a line in docs/api.md "Not yet bounded"):
 1. tiered current-member listing: NodeIDsByLabelMetered / RelIDsByTypeMetered
    (tiered/tieredstore_member_page.go:102,125) charge each closed shard's open only; every shard's member list is
    built and merged (mergeNodeIDSlices, slices.Compact) before the core counts a member. Under a ShardOpens bound
    the core does not ask the store for its member count first (api.md effective-scans bullet).
 2. tiered ex-adjacency: exAdjRelIDsCharged (tiered/tieredstore_exadj.go:83) collects a seed's ex-adjacent IDs
    from every shard it opened before the core's callbacks count them (api.md remaining-scans bullet).
 3. the history fold of several labels on a store without the ever-member sidecar (sharded; core temporal.go):
    the store's fold builds the ID union before the gather sees it (api.md effective-scans bullet).
 4. the first build of a RAM membership sidecar (K1, one scan of the label's or type's rows) and of a value's
    RAM window view's first build when the value fits the room (api.md: built once, the first reader pays).
 5. ValidEndAfter: the pruning door counts Candidates only, no DecodedBytes (api.md).
 6. badger LabelTxMembersOf (badger/badgerstore_labeltxmembers.go:543): to say which of a few IDs are members it
    builds the label's whole current-member set (a keyspace walk under LabelIndexOnDisk); it takes no tally.
    Found with R2-2 (same class). Reached from the core's point membership checks (LabelTxMembersOf callers).
 7. badger labelNodeIDsSnapshotTalliedLocked (badger/badgerstore_label_disk.go:81) ranges the whole write buffer
    (rangePending, flushing + pending) to find one label's buffered ops; the ops of other keys are visited
    uncharged. rangePendingPrefixes (by the 3-byte label prefix) would visit only the label's ops. Found with R2-2.
 8. the valid-end index's candidate list (built from RAM, counted as BufferBytes after it is built) and its RAM
    walk (api.md remaining-scans bullet).

B. Charged by the candidate count already paid, recorded so a later reader does not re-flag them:
 - badger keepLabelledLocked (badger/badgerstore_node_query_ids.go:116): one label-key probe per index match, under
   LabelIndexOnDisk; each match was counted as a candidate before (the property index walk), one probe each.
 - badger labelCurrentMembersTalliedLocked (badgerstore_labeltxmembers.go:611): the set built from a disk walk
   whose every key was charged as it was visited; the set itself is not BufferBytes (a store buffer, api.md:
   "the stores' own buffers are not counted" except where a later item names them).

   copy.
