RELHIST design (read-only trace, main ee10a85b, 3 Nov) — sigma's GC analysis, tiered, paging off

1. Trace: which doors reach the whole relationship history

Sigma's listed doors are node doors; none touches relationship history:
- NodeEffectiveTimeline: effective_timeline.go:400 -> head cache (nodeHeadSegments, effective_head.go:640-665: current row + one
  point read per winner), else temporal-meta skeletons (:620-682: a prefix walk of every version's temporal block,
  badgerstore_temporalmeta.go:54-118, then a point read per winner), else the whole node history.
- NodeEffectiveTimelines(id, pins): effective_timelines.go:40-213. "The head-pin cache is neither read nor filled" (:39, :114-116):
  every call walks every version's skeleton (:160-198), O(versions) even at the head pin.
- NodeEffectiveTimelineFrom, ForEachNodeEffectiveByLabelAndProperties (effective_page_by_props.go:32 -> :124, scan mode),
  ForEachNodeEffective(From) (effective_scans.go:90; rd.scan: head cache bypassed, effective_scan_reads.go:59-61,
  effective_timeline.go:583): the same node path. LendByIDs: current rows only.

So getRelHistoryByPrefix / reconstructRelHistoryWire / DeepCopy come from the write side or from rel doors the cut calls itself.
Runtime callers of core.getRelHistory (store_fetch.go:174):
a) GraphTx delete of a rel, or of a node with rels, on tiered: tx_mutations.go:455, :520 -> deletedRelHistorySnapshot :671-688:
   `if tx.g.historyTrim == nil { history, err := tx.g.copyRelHistory(id) }` (:672-673): whole history + DeepCopy per row
   (tx.go:432-445). nativeHistoryRollbackTrim admits only *memory.Store and *badger.Store (core.go:1608-1610); tiered has no
   Trim*HistoryFrom, so there historyTrim is nil and EVERY tx delete copies the whole chain; nodes alike (:657-669). The one caller
   that is O(versions) per write whatever the pin, and DeepCopy-shaped: my prime suspect.
b) A tx update whose chain has a row at or above the current version (tx.go:391-409): rare; otherwise one page read.
c) Rel corrections (SetRelVersionInterval / excise) on a head-cache miss: temporal_cascade.go:1015-1016.
d) Re-import of a deleted rel ID: relLifeStart, version_alloc.go:300-327 (presence bit first).
e) Rel doors of ai-soc's shape: RelsDuring/RelsDuringTx/RelsRelating/ByTypePropertyDuring and their GraphTx twins
   (temporal_queries.go:255/379/1624/1649, tx_consistent_reads.go:487/629) -> findRelVersionMatchingDuringTx temporal.go:1672-1690:
   whole history, no head cache, no skeletons; Rels().History (crud.go:78). ForEachAdjacentRelAt with a temporal filter uses
   singleVersionAdjacency (adjacency_version.go:159-186: presence bit + point reads), not the history.
f) RelEffectiveTimeline (effective_timeline.go:555-611), RelsEffectivePage, ForEachRelEffectiveAtNodes: skeletons + point reads;
   the whole history only when a winner vanished (:594).

Why it grows: every caller is O(versions of the key) per call and sigma's keys gain a version per cut. The head cache does not
help: (i) the plural door never reads it; (ii) a plain Update bumps the key's history epoch (effective_head.go:28-31, headValid
:274) and only cascades overlay the entry (relHeadAfterWrite from temporal_cascade.go:1182 only; nodes :409), so a write-then-
read-back misses per key per cut and folds the skeletons again — invalidation is per key, not per cut; (iii) scan mode bypasses it
by design ("repeated point reads of a small hot set", effective_scan_reads.go:59-61).

Per version, getRelHistoryByPrefix (badgerstore_history_rel.go:375-454) allocates KeyCopy (:392), a value copy (:398-399), a map
entry and key string (:382, :396), the sorted key list (:430-434), the wire (SafeUnmarshal :197 or anchor+delta :202-222), the
decoded row (:447) and a second full row by DeepCopy (:451): about four row-sized copies. The "fresh decode, no second copy" rule
already holds for GetRelVersion (:301, :328); :451 and :562 contradict it.

z.Calloc (18 %): badger decompresses a block into a fresh buffer on each block-cache miss (table/table.go:785-815, badger v4.9.2;
badger.md:130-131). A prefix walk touches every block holding one of the key's versions and opens table.NewIterator per table whose
key range covers the prefix (badger.md:122-125): a key whose versions land in a new table each cut costs one iterator and one block
per cut of age. Fewer whole-chain walks is rho's only lever; compression itself is NOCOMPRESS (todo).

2. Proposals, ranked by gain/risk (13.1 GB a cut: rebuild 8 % = 1.05 GB, Calloc 18 % = 2.4 GB)

P1 (ask 1, write side) — tiered tx snapshots trim instead of copying. (a) Patch: in deletedRel/NodeHistorySnapshot, when
  historyTrim is nil but the store pages (historyVersionPageCapability; tiered: tieredstore_read_history_rel.go:126), snapshot only
  the rows at or above the deleted row's version (one page, usually empty) and roll back by TruncateRelHistory(id, keep) plus a re-put
  of that page; the rows below are untouched by the delete. (b) Minor: tiered gains Trim*HistoryFrom routed to the owner shard like
  TruncateRelHistory (tieredstore_write_history.go:234-318), admitted at core.go:1608. Semantics: rollback state identical, reads
  unchanged. Saving: the whole 8 % where a) is the caller (DeepCopy 0.48 + reconstruct 0.39 + prefix 0.32 GB) plus that walk's share
  of Calloc and NewIterator. Red test: tiered, a rel with 64 versions, tx Delete then Rollback, history byte-equal; a node with its
  rels; c.historyRead counts <= 1 page. Mutations: restore the copy branch -> the count fails; drop the truncate -> equality fails.

P2 (ask 1, read side, nodes and rels) — head answer for the plural door and across plain appends. (i) NodeEffectiveTimelines /
  RelEffectiveTimelines read the head entry when rd.snap == nil, !rd.scan and every pin >= e.maxTx (headValid), and fill it from
  their fold otherwise (effectivePiecesFacts + noteNodeHead as effective_timeline.go:606-608). Sigma's pin at the round's tx is
  >= maxTx in the common case: current row + point reads per winner, no skeleton walk. (ii) After a plain Update / ReplaceVersion /
  CloseVersion, overlay the entry with the appended row as a cascade does (headOverlay, effective_head.go:38-57: the append is the
  newest belief, replaces nothing, tiles with the old current row's end); where headOverlay refuses, drop as today. Semantics: the
  differential test (effective_head_test.go) compares the cached answer with the fold at every pin. Saving: removes the O(versions)
  skeleton walk per read-back; sized against rho core 24 % (paintHeadAll, hash32.String from skeleton decodes), not the 8 %; at 100
  versions ~99 fewer partial decodes and nearly all block touches of the read. Red tests: c.headHits rises on the second plural call;
  after Update the entry stays valid; the oracle test with Update-then-plural-read at the head pin. Mutations: skip the overlay ->
  headHits 0; wrong maxTx -> differential test red. Overlap: HEADLEND's lend applies to the plural door's winners; build on it. Patch.

P3 (ask 3) — decode inside item.Value in getRelHistoryByPrefix (node twin, read snapshot badgerstore_read_snapshot.go:729-745).
  Badger: the value is valid only inside fn and until the next iteration (iterator.go:28-30, 76-82; badger.md:321-323), which
  historyTemporalMetaByPrefix honours (badgerstore_temporalmeta.go:73, 88-95). Keys ascend by version and an anchor's version <= its
  deltas', so keep only the last decoded FULL anchor wire as localAnchor; merge overlay rows in order (:104-116); drop the map, key
  strings, sort, value copies and the DeepCopy at :451/:562. Rows equal. Saving: ~3 of 4 copies per version, 0.6-0.7 GB of the 1.05 GB
  (5 %) for every remaining whole-history caller (c, d, e). Red test: bytes per version on a 64-version rel with deltas on, <= 2
  allocations a row; a delta whose anchor sits in another table. Mutations: reinstate DeepCopy -> bound fails; use the raw anchor
  after Next -> wrong row. Patch.

P4 (ask 2) — per-key reconstructed-history cache keyed (kind, id, history epoch): the epoch is the head cache's invalidation token
  (effective_head.go:28-31), no per-cut flush; byte-bounded as headCache (:62-81), e.g. 64 MB, never per entity at 2 TB/day; rows
  frozen and lent (HEADLEND discipline). Pays only when one key's history is read more than once per epoch; after P1-P3 the remaining
  readers read a key once per cut. Rank last; needs sigma's per-key read count. Minor if it adds a Config field.

4. P1 as built (branch histtrim, 3 Nov evening) — sigma's cut-10 profile changed the target

Sigma's frames (tiered, cut 10, 160 GB alloc_space): getRelHistory 32.0 GB = copyRelHistory under GraphTx.snapshotCurrentRelLocked
(the UPDATE snapshot, not deletedRelHistorySnapshot) 16.1 GB + cascadeRelMode 15.9 GB; snapshotCurrentRelLocked's own total 26.9 GB
(copyRelHistory 17.8, relHistoryAtOrAbove -> RelHistoryVersionsFrom 8.1, DeepCopy 0.4).
- Which branch copies: snapshotCurrentRelLocked (tx.go:366-417 on main) skips its two cheap shapes when (a) the head entry is invalid
  and (b) relHistoryAtOrAbove finds a row at or above the current version. (b) is the normal state after a correction or a whole-axis
  untimed update of an entity with valid-time segments: the cascade appends a row per segment, only one takes the current slot, the
  others are history rows ABOVE the current version (probe: 4 updates + one bounded correction -> current v4, history v0-v3, v5, v6,
  no head entry). Then copyRelHistory copies the whole chain on EVERY store, historyTrim or not. So the minor form (b) of section 2,
  tiered Trim*HistoryFrom, would not have removed the profiled 16.1 GB: the found branch never looks at historyTrim.
- Why RelHistoryVersionsFrom costs 8.1 GB: the found check pages ONE full row (limit 1): badger value copy, reconstructRelHistoryWire
  (plus a point read of the anchor when the row is a delta whose anchor lies below the page), decode, DeepCopy
  (badgerstore_history_rel.go:456-565), and an iterator per table. A key-only probe would answer "any row >= v", but the row is
  needed anyway: it is exactly what the snapshot must keep.
- The fix (patch form, no exported name): the snapshot keeps the trim point and COPIES THE ROWS AT OR ABOVE IT, one page read
  (snapshotNodeHistoryFrom / snapshotRelHistoryFrom, limit 0, replacing relHistoryAtOrAbove + copy*History); empty unless a correction
  left rows above the current one, then those rows only (bounded by the last cascade's segments, not by versions). Rollback
  (restoreNodeHistoryFrom / restoreRelHistoryFrom): with the rollback trim (memory, badger) trim from the current version and put the
  copied rows back; without it (tiered, sharded) read the chain at rollback, keep the rows below the trim point, append the copied
  rows and rewrite (truncate + put, the old copy path's own restore). Sound because a tx writes no history row below the current
  version of the entity it snapshots (corrections append; update and delete move the current row in at its own version) — the
  assumption the trim and the head-entry (68b) snapshots already make — and any row it writes at or above is removed and the
  pre-tx rows put back. Same for deleted nodes and rels (deletedNode/RelHistorySnapshot) on every store with a pager: on tiered a tx
  delete no longer copies the chain at all. Re-import after a delete in the tx materializes rows below + the copied rows.
  ADR-0010: a foreign-incoming stub's ErrSlotNotLocal keeps its old outcome (delete: no history snapshot; update: the trim point).
- Caveat (pre-existing, recorded as an item): history compaction or a retention purge that runs between a tx's ops (it is
  not a tx door and does not take the tx's entity snapshot) can trim a row the snapshot copied; rollback then puts that row
  back. The old whole-chain copy did the same (it restored every copied row), so rollback has never been compaction-aware;
  the page form narrows it to the copied rows at or above the current version.
- Review round (Fable found nothing blocking): the equality guard now also runs on sharded (pager, no rollback trim: the
  rewrite branch), on void rows above the current version (an excise), on a chain holding a tombstone (delete and
  re-import, then a correction), on delta-encoded badger (anchor interval 4: above-rows that are deltas on an anchor below
  the trim point, and a trim point at an anchor version), and the legacy row-at-the-current-version case runs on badger
  and tiered as well as memory (TestRELHISTTxRollbackRestoresShapes, TestGraphTx_*CurrentVersionHistoryExists); each with
  a mutant it kills (p1-mutations.txt, round 2).
- Why not the minor form as well: tiered Trim*HistoryFrom (routed like TruncateRelHistory to every source) would only make the
  ROLLBACK of a tiered tx O(page) instead of O(versions); the write path is already O(page). Two new exported methods for a rollback
  cost the cut never pays is a door with no consumer request; nativeHistoryRollbackTrim and its wrapper check stay unchanged.
  Revisit if a consumer rolls back often on tiered.
- Cost (TestRELHISTTxSnapshotCopyBounded, rows copied by the snapshot, tiered Signal): delete rel N=1/10/100: 0/9/99 -> 0/0/0;
  delete node with rel: 0/18/198 -> 0/0/0; update rel above current: 0/11/101 -> 0/2/2; update node above current: 0/11/101 -> 0/2/2.
- cascadeRelMode's whole-history read (15.9 GB, not changed here): on a head miss (chainFromCurrent fails for a multi-segment
  entity, chainFromHead has no valid entry) temporal_cascade.go:1014-1035 reads every row. It needs full rows only for the bases of the
  segments it patches (the winners in [newVF, newVT), every winner for a whole-axis update) and for the resumption source; every
  other row contributes only version, temporal block, void and delete flags (maxVersion, chainStamps, bounds, txOrdered, voidFree),
  which RelHistoryTemporalMeta gives without decoding properties. The fix is section 2's P2 applied to the write side: on a miss,
  fold the skeletons into a head entry (prep.head's facts) and plan from it with a point read per winner (chainFromHead), as
  nodeEffectiveViaTemporalMeta does for reads. Why the entry misses on sigma's keys is not known: a chain with a delete or retraction
  never qualifies (gatherHeadFacts), the byte cap evicts, any non-cascade write bumps the epoch. Next item, with that question to
  sigma.
- NodeHistoryTemporalMeta via historyAcrossShards (10.9 GB): its only core callers are entityReads.nodeMeta from
  nodeEffectiveTimelinesOf (effective_timelines.go:161, the plural door, every call), nodeEffectiveViaTemporalMeta
  (effective_timeline.go:621, the singular door on a head miss) and nodeAtViaTemporalMeta (temporal_queries.go:588, node-at reads).
  Not changed here (P2).

CASCADEMETA (next item, Fable design 3 Nov 23:00, key claims checked in source here):
- Cause on sigma's shape: gatherHeadFacts (effective_head.go:312) refuses a chain with a delete, a retraction or a
  shared version, so prep.head is nil and every cascade on such a key misses and reads the whole history. A head entry
  for such chains is the wrong fix: entries serve reads too, and the read fold caps lives and drops retracted ones
  (chain_resolver.go:260-276) while the cascade resolver uses no caps (temporal_cascade.go:560).
- Fix (a patch, unexported only): on a miss, when c.temporalMetaHistory != nil, build the stub chain from
  RelHistoryTemporalMeta / NodeHistoryTemporalMeta (as relEffectiveViaTemporalMeta, effective_timeline.go:685-704) and
  run preCorrectionChain, prepareCorrection, segments, winnerAt, resumption end, cascadeNewCurrent and prep.head on it
  unchanged; read full rows (getRelVersion, memoised) only for each segment base and the resumption source; the template
  is the current row. Fall back to the whole history when versions are not strictly ascending, one equals the current
  version, or a point read fails. sharded.Store has no skeleton door (only its read snapshot), so sharded keeps the
  whole-history path; adding the door there would be a minor.
- Untimed Update of a rel with valid-time segments is cascadeExisting (whole_axis_write.go:81): every winner is a base,
  so k full rows stay (k distinct winners, not N versions).
- Corrections to the above: the head cache cap is a weight (pieces + bounds + 1, 16,384 per stripe), not bytes, and a
  put over the stripe's share drops the whole stripe (effective_head.go:200-206).
- Tests: red counting test (no GetRelHistory on the miss path, full-row reads <= winners + 1; sharded pins the
  fallback); twin equivalence with the skeleton path off (bounded, open, excise, whole-axis, retraction + re-import,
  tombstone in chain, legacy shared version, pre-migration chain, order-rule refusal, compaction between reads); cost
  bound at 64 and 1,024 versions. Estimate (inference): about 5x less allocation per cascade miss.

RELHIST P5 design: bounding NodeHistoryTemporalMeta (sigma: 10.9 GB via historyAcrossShards). Fable, read-only, main v4.104.7,
4 Nov; the lead checked these claims in the source: headValid's lowest-pin rule (effective_head.go:272-281, :701), gatherHeadFacts
refusing any delete/retraction (:315), a put over the stripe weight clearing the whole stripe (:207-209), NodeBeliefWatermark only on
memory and badger, no NodeHistoryTemporalMeta on sharded.

1. Callers (four): plural door rd.nodeMeta (effective_timelines.go:174-175); singular door on a head miss (effective_timeline.go:621);
   node-at doors via nodeAtViaTemporalMeta (temporal_queries.go:588; batched_attx.go:61; temporal.go:1551, :1566); cascade miss plan
   nodeMetaPlan (cascade_meta.go:157). Per version: badger one block visit + partial decode + one heap TemporalMetadata; tiered walks
   one shard (event), the reference shard plus the archive, or every history shard (not live), then copies and re-sorts the merge
   (tieredstore_history_meta.go:73-158); sharded has no skeleton door, so plain reads take the whole history with full rows. Core adds a
   stub node per version and folds O(V log V) per pin in the plural door.
   Why sigma's shape reaches it: (1) a plural call with a pin below the newest TxFrom misses (lowest pin tested, highest filled);
   (2) a chain holding a delete or retraction never qualifies: permanent O(V) per read; (3) the entry survives only Update / GraphTx
   UpdateNode / Batch / ingest (headSupersede), not property CAS, replica apply, Delete, corrections; (4) a put over the stripe share
   clears the stripe, an entry whose validity moves each cut weighs ~2V; (5) scan doors never use the entry; (6) node-at doors on
   tiered have no belief watermark: every NodeAtTx with history walks all skeletons; (7) a restart empties the entries.
2. Options: A head entries for chains with deletes/retractions (maxTx = max(TxFrom, DeletedAt), A1 reads only, A2 extendable across
   writes when every delete precedes the appended row; core patch, no format change); B append-only refresh of a stale entry from a
   version floor (needs a second per-ID token moving only on deletes and on sets at or below the presence top; new capability: minor);
   C keep the superseded entry as a second generation for pins straddling a cut (core patch); D node-at from the entry (core patch) or
   a tiered belief watermark (minor); E store-side skeleton cache (last); F cheaper skeletons (constant factor, after the O(V) is gone).
3. Recommendation: Phase 0 (patch) a miss-reason counter on the head doors (no entry / token moved / current changed / pin below maxTx
   / not whole / chain not qualifying / scan door / node-at door), then sigma's counts for one cut decide among A-D. Phase 1 (patch)
   A1+A2: the cause certain from sigma's own words (deletes of retracted facts). Oracle: the head differential test extended with
   tombstone, retraction, retraction + re-import, delete then Update of the re-imported life, pins between delete and re-import, on all
   four backends. Cost gate by counts (skeleton lists read, history rows, head hits), not MemStats. Mutations: gatherHeadFacts still
   refusing deletes, headSupersede refusing extendable=false, maxTx without DeletedAt, A2 extending past a later delete.
   Phase 2 by the counts: B (token moved without supersede, restarts), C (pin below maxTx), D (node-at doors).
4. Asks to sigma (cuts 10 and 30): which node doors the cut calls and with which pins; how a rewrite is written (Update / GraphTx /
   Batch / ingest vs CAS / Delete + re-import / ReplaceVersion) and whether its validity moves each cut; the share of keys with a
   tombstone or retraction; distinct keys read per cut and restarts between cuts; where the facts live on tiered (event, reference,
   neither); whether a key's history is read more than once per cut; alloc_space split by NodeHistoryTemporalMeta's parent frame.
