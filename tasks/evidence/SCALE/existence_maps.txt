Heap profile after the 2 M reopen (inuse_space, 568 MB):
  237 MB  ristretto z.Calloc       badger block cache, filled by the open scan; capped (BlockCacheSize)
  166 MB  skl.newArena             memtables; fixed per writable shard (CACHE: ~88 MB + 18 goroutines)
   65 MB  bumpNodeRevLocked        nodeRevs map[NodeID]uint64: 32.5 B per node
   60 MB  loadIndexesScan.func1    nodeIDs map[NodeID]struct{}: 30 B per node
  (relIDs / relRevs are the same pair for relationships)

Reading: the bounded parts are caches; what grows without bound is ~63 B per node (+ the same per rel)
in every open shard, and a clean open that walks every node key to fill them (~1.4 s per 1 M nodes).

At the SCALE goal (2 TB a day, ~4 billion 500-byte facts):
  - a day-shard's maps: 4e9 x 63 B ~ 250 GB of heap while it is open (hot and warm shards are open);
  - its clean reopen: ~4e9 / 1 M x 1.4 s ~ 90 min; a crash reopen (~10 s per 1 M, CHAIN) ~ 11 h;
  - the reference shard (ai-soc's Derived) is always open and grows for ever: both costs grow with
    the store's total, not with a window.

property; ai-soc's tiered config, label and adjacency indexes on disk; 1 M nodes of 100 B, main and branch
alternated):
  1 M nodes + 1 M rels, clean reopen:  main 1.28 / 1.22 s, heap +376 MB   branch 0.11 / 0.16 s, heap +211.5 MB
  1 M nodes only, clean reopen:        main 0.22 s, heap +213 MB          branch 0.07 s, heap +189 MB
  insert unchanged (55-61 k/s both).
Before, rels cost ~163 B of heap and 0.86 s per 1 M at open: the open walked the KeyOut and KeyIn keys though the
disk mode keeps none (~410 ms), counted every label key, and rebuilt the RAM rel-type index from every KeyRelType
key (~360 ms; a map per type, ~36 B per rel), and the walks filled the block cache (~129 MB). Now the image holds
the label counts and the rel-type index (an ID set per type), so with both indexes on disk a clean open walks no
key per entity; RAM per rel 49.7 -> 16.2 B (TestOpenWalkResidentBytesPerRel, budget 24 B).
