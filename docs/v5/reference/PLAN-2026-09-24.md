# tkg v5 plan

Status: DRAFT for owner review (2026-09-24). Branch `v5`, module path
`github.com/data-insights-ai/rho-tkg/v5` once code starts.
Base: v4.37.2 (`0659ecef`) plus the review of the "temporal graph implementation
v1.3" handoff (a Rust distributed-server specification).

v4 stays the production line on `main`: bug fixes and releases continue there.
v5 is a new engine built beside it in Go. It reuses proven v4 pieces
(segment codec, trust-boundary decoding, integrity primitives, test discipline)
but not v4's data model, write path or backend structure.

Every number below is marked **measured** (with its source) or **target**
(to be measured at the named gate). Targets are not results.

---

## 1. Why a v5

v4 is correct per entity and well tested (about 123k lines of code, 240k lines of
tests). Its foundations were chosen for an embeddable per-entity graph with wall-clock
history. The direction is now a bitemporal store for SOC telemetry at up to about 1 TB of
raw input per day on one NVMe-backed machine (ADR-0011 §1.1). Several v4 foundations
work against that direction, and their costs show up as the recurring defect classes in
the changelog.

### 1.1 Measured state of v4

| Fact | Source |
|---|---|
| ~744 B and ~13 heap objects per relationship (memory store), linear in the day | ADR-0011 §1.1, S0 re-measured 718–723 B |
| badger as ai-soc configures it: 1,043 B/rel resident; per-rel planner-stat memos held 2.12 GB of an 8.04 GB heap | ADR-0011 §1.1 |
| badger open decodes every node and relationship row (`loadIndexesScan`) | `badgerstore.go` |
| segment codec S1: 22–25 B/HOP on disk, column-only decode 24–28 M rows/s | CHANGELOG 4.37.0 |
| replay adapter, strong ingest mode: 8,815 rows/s | `tasks/evidence/temporal-index`, ai-soc |
| 174 release headings in 7 months; the recent HIGH fixes cluster in the badger cache/overlay/flush window (4.37.1, 4.27.0, 4.25.0) and cross-backend divergence (4.29.0) | CHANGELOG |

### 1.2 Confirmed v4 semantic defects (probe tests, 2026-09-24)

1. `GraphTx` is write-through with compensating rollback. An outside reader sees
   uncommitted rows; a standalone write between two tx calls is erased by `Rollback`.
   (Documented as the v4.1.0 trade-off on the v4 line.)
2. Deleting a previously closed entity changed the answer of an earlier as-of read
   (closed entity reappeared as open-ended at a pin before the delete).
3. `SetNodeVersionInterval` copied today's property values into the corrected past interval.
4. Endpoint masking differed between doors (`RelsAt` vs `Snapshot` vs `OutgoingRelsAt`).

Items 2–4 are fixed on the v4 line (`fix/v4-temporal-semantics`). They are listed here
because each one traces back to a foundation v5 replaces (§2).

## 2. v4 foundations and what v5 does instead

| v4 foundation | Observed consequence | v5 decision |
|---|---|---|
| Transaction time = wall-clock ms per operation with a monotonic floor (`c.now()`); one tx gets many stamps | As-of pins are not reproducible in several traced cases (backfill, future valid-from stamping, unclean shutdown, in-flight writes at `NowTx`); two selection rules (version order vs TxFrom) | **System time is a logical commit sequence** (`CommitSeq uint64`), one per committed transaction, assigned by the commit sequencer. Wall-clock observation is stored once per commit and indexed; "as of timestamp" resolves to a `CommitSeq` through that index. |
| Valid time per whole entity version; interval derived from neighbour rows, `UpdatedAt` fallback, snowflake mint-time fallback | Past corrections must copy a whole row (defect 3); valid time silently equals transaction time when unset; closed-then-deleted rows ambiguous (defect 2) | **Per-component valid-time functions**: presence (lifecycle), each label, each property is an interval map. Validity is explicit on every mutation or comes from a declared per-type default. No derivation from mint time or `UpdatedAt`. |
| No lifecycle concept; delete = in-place tombstone; re-import of a deleted ID reuses version numbers | Defect 2; re-import after delete overwrites old history (traced) | **Lifecycles** (`LifeId`): create, close, reopen, correct. Edges bind to endpoint lives. Delete is a lifecycle close plus an explicit, separate erase operation for retention. |
| Masking decided per door | Defect 4 | **Visibility is a read parameter**: `Declared` (own assertions) or `Effective` (lifecycle and endpoint masking), same rule for every access operation. |
| Schemaless `PropertySlice` of `any`, reflect validation, registered custom structs | 256+ B properties per rel, boxing, GC load, reflect-heavy hashing and wire code | **Typed schema** per label / relationship type (property id, type, cardinality). A dynamic property bag remains available as one typed variant column; values are never Go `any` in storage or on the hot path. |
| In-RAM indexes and ID sets are the source of truth while running; rebuilt at open by decoding all rows | Open time and resident memory grow with history | **Everything durable is paged or in immutable segments**; RAM holds bounded caches and the memtable. Open cost is proportional to manifests, not data. |
| Async write buffer + entity cache overlay + badger snapshot, reconciled by flush epochs | The dominant HIGH defect class (stale/dropped rows across flush and eviction) | **One write path**: WAL (group commit, explicit fsync policy) → arena memtable with MVCC by `CommitSeq` → sealed column segments. A read is a snapshot at a `CommitSeq` over memtable + segments; there is no separate cache-coherence protocol. |
| Four backends (memory, badger, tiered, sharded) each implementing the full Store interface and many optional capabilities | Every feature is multiplied by backends × doors; cross-backend divergence fixes | **One engine.** In-memory mode = same engine on an in-memory VFS. Tiering = segment placement policy. Partitioning = a partition key inside the engine. The v4 memory store's role as differential oracle moves to the pure reference model (§4.1). |
| Snowflake IDs: 48-bit µs from 2026-01-01, 16 node slots, time used for shard routing | ID space ends 2034-12-02 (arithmetic: 2^48 µs); routing depends on mint time | **64-bit range-allocated IDs** with a partition tag and no clock dependence (decision D2). Dense `uint32` ordinals inside segments. |
| Per-entity SHA-256 chain, 64-char hex string held per entity (~190 B/rel with `RelIntegrity`) | Memory and hashing cost on every write | **Per-commit hash chain** (commit envelope digests its effects and the previous commit) plus per-segment integrity blocks (ADR-0011 §4.3). A per-fact content hash stays computable and can be stored as a 32-byte binary column where a consumer needs it (sigma-tkgd `tkg_hash` provenance anchor). |
| Separate co-committed change-log (`0x09`) beside the data | Two logs to keep consistent; replica bootstrap from export | **The WAL/commit directory is the change feed.** `ReadChanges(fromSeq, toSeq]` and replicas read it directly. |
| Many bespoke temporal methods plus generic `QueryOpts` doors ("two doors, same shape") | Rule 17 exists because fixes had to be applied twice | **Small access contract** (§3.5): one snapshot handle and a handful of batch operations. |

## 3. v5 model and engine

### 3.1 Time

- `CommitSeq uint64`: the system-time coordinate. Strictly increasing per partition,
  one per committed transaction, persisted in the WAL. The all-zero value is the empty history.
- Commit directory: `CommitSeq → {observed wall time µs, actor/source metadata, request id,
  effect references, prev commit hash, commit hash}`. Actor and source are stored once per
  commit, not per fact.
- Valid time: `int64` UTC microseconds, half-open `[from, to)`, with explicit `-inf` / `+inf`
  bounds (`from < to` required).
- Backfill of historical knowledge (v4 `AllowTxBackfill`) becomes explicit metadata: the
  import keeps the source's recorded times as a mapping (`source_recorded_at`) and never
  writes a `CommitSeq` below the current head.

### 3.2 Objects, lifecycles, components

Semantics follow the handoff's C04 section and its 16 executable fixtures, copied to
`docs/v5/reference/` (§4.1). In short:

```
presence(obj)            : valid_time -> LifeId | Absent
label(vertex, life, L)   : valid_time -> bool
property(owner, life, k) : valid_time -> Value | Absent   (scalar)
                           valid_time -> Set<Value>        (set)
edge                      : immutable (type, source, target); each edge life binds
                            to one source life and one target life
```

- `SET k=v over [a,b)` replaces exactly that interval and preserves both tails; `UNSET`
  removes exactly that interval; adjacent equal runs merge.
- Close/reopen/correct operate on lives; reopening allocates a new `LifeId`; a correction
  edits the same life and restores its children where effective visibility returns.
- Absent and present-null are different.
- Property and label writes must be covered by the owner's own declared life
  (`OWNER_VALIDITY`); edge creation must be covered by both endpoint lives.
- Endpoint masking is applied at read time under `Effective` visibility, never by
  rewriting edges.

### 3.3 Physical layout: one reducer, two shapes

Most SOC volume is append-mostly relationships whose component timelines collapse to one
interval (ADR-0011 "declared bulk" types). For those, a segment row is
`(id, life, source ordinal, target ordinal, valid_from, valid_to, commit_seq, typed columns…)`,
which is the ADR-0011 row shape plus `life` and `commit_seq`. Entities with evolving
attributes store component timelines as a base plus bounded patches (the v4 anchor+delta
idea, per component). Both shapes are decoded by the same interval reducer; homogeneous
blocks encode their common interval or `CommitSeq` once per block.

### 3.4 Write path and transactions

1. **VFS** abstraction for every file operation, with an in-memory and a fault-injecting
   implementation for tests.
2. **Transactions** run optimistically on a private write set; reads record the
   component revisions they depended on. Nothing is visible to other readers before commit.
3. **Commit sequencer** (one per partition): validates the read set against revisions
   committed since the transaction's snapshot, assigns the next `CommitSeq`, appends one WAL
   record for the whole transaction (group commit across transactions), applies it to the
   memtable. A transaction is atomic and serializable; a conflict returns `ErrConflict`.
4. **Durability policy** is explicit per graph: `Sync` (ack after fsync of the group) or
   `Buffered` (ack after WAL append, fsync on interval). The loss window of `Buffered` is
   reported in the docs and in metrics.
5. **Memtable**: arena-allocated, offset-based (no Go pointers per fact), MVCC by `CommitSeq`.
6. **Seal**: a full memtable becomes immutable column segments (ADR-0011 codec, extended)
   and a new manifest version; the WAL is truncated only after the manifest is durable.
7. **Ingest** uses the same sequencer with larger groups; producers do validation and
   encoding in parallel (v4 ADR-0006 prepare/apply split carries over).

### 3.5 Access contract

A consumer opens a snapshot and runs batch operations against it:

```
Snapshot{ Cut: CommitSeq | Latest, Valid: Point(t) | Interval(a,b) | All,
          Visibility: Declared | Effective }

Lookup(ids, projection)                   -> column batch, one row per input
Scan(type|label, projection, filter)      -> column batches, resumable
Expand(frontier ids, direction, types)    -> grouped adjacency batches
Timeline(ids, components, valid window)   -> per-component interval runs
Changes(fromSeq, toSeq], selectors)       -> committed effects in order
Diff(snapshotA, snapshotB, selectors)     -> net signed differences
Stats(type|label)                         -> cardinalities, degree, fragmentation
```

- Output is column batches with typed buffers, at most 4,096 rows per batch; the Arrow
  dependency is decision D5.
- Filters are exact same-row comparisons; anything the engine cannot evaluate exactly is
  returned to the consumer as unevaluated.
- Joins, aggregation, recursion and the query languages stay in the consumers
  (sigma-tkgd's Cypher planner, ai-soc).
- A snapshot handle can be serialized and reopened later at the same cut while retention
  covers it.

### 3.6 Indexes

- Mandatory: ID → location directory, out/in adjacency, system-time (commit directory),
  valid-time.
- Opt-in and declared in the schema: label, property equality/range, composite.
- Each index publishes the `CommitSeq` it covers; a read at a later cut combines it with the
  memtable delta, or falls back to a scan.
- **Current-state accelerator**: a "valid now" read must not scan ended history. With 10,000
  closed edges and 10 live ones, a current expansion examines the live base plus the
  unapplied delta (the handoff's `current_index_history_amplification` case).

### 3.7 Memory and garbage collection in Go

The GC cost in v4 comes from the number of live pointer-bearing objects (about 13 per
relationship, measured). v5 rules:

- No Go pointers per fact: facts live in `[]byte` arenas, mmap'd segments and `uint32`
  ordinal arrays; strings are dictionary codes.
- Bounded caches hold pages, not objects.
- `GOMEMLIMIT` set from the configured memory budget; allocations per batch and per row are
  reported by the benchmarks and gated.
- Batches and decode buffers are pooled per operation.

Targets for the gates in §5: resident memory independent of history size; GC CPU and p99
pause reported for every benchmark.

### 3.8 Integrity, replication, operations

- Commit hash chain plus segment integrity blocks; `Verify` walks commits, segments or one
  entity's component history.
- Replication ships WAL records; a follower serves snapshots at its applied `CommitSeq`
  and reproduces the primary byte for byte (the v4 guarantee, now for free because the WAL
  is the source).
- Backups copy immutable segments plus the WAL tail; incremental backups copy new segments.
- Retention drops or rewrites whole segments; erasure writes an erase mask and rewrites
  affected segments.
- Tiering moves sealed segments between NVMe and object storage by access statistics.

## 4. What v5 takes from the v1.3 handoff

### 4.1 Adopted now

- **The temporal semantics and fixtures.** `docs/v5/reference/temporal_oracle.py` (274
  lines) and `temporal-fixtures.json` (SEM01–SEM16: the Austria/Germany correction, tail
  preservation, lives, endpoint-bound edges, set properties, absent vs null, pointwise
  uniqueness). Phase V0 ports the oracle to Go and runs every fixture against the engine.
- Logical system time, one stamp per transaction, wall-clock as a separate mapping (C01.1, C08).
- Lifecycles, declared vs effective visibility, owner-validity checks (C04).
- Commit envelope storing actor/source/request once; per-effect references (C09.1).
- Bounded patch chains with base consolidation; count rewrite amplification (C09.2).
- Current-state accelerators beside historical candidates (C10.1).
- Snapshot descriptors that can be reopened; `ReadChanges` vs `DiffSnapshots` distinction (C13.4).
- Typed error codes as a closed list.
- The rule that an unused feature costs zero bytes per row, and a byte ledger in every
  benchmark (C19).
- Deterministic crash/fault testing of the write path (the simulation idea of C18, applied
  to one process).
- Storage owns access paths; consumers own query semantics (C13.1). v4 already follows this.

### 4.2 Adopted later (phase V7, only if measurements require it)

Partitioned ownership with Raft replication, dependency footprints and local fast path,
cross-partition commit, certified cuts across partitions, placement/moves/splits. The
handoff's `CommitFrontier.tla` is the starting point for that phase; it has not been run.

### 4.3 Not adopted

- The Rust stack and the 34-task sequential plan.
- Spatial domains, evidence/annotation sidecars as core features (revisit if a consumer asks;
  the zero-cost rule applies).
- Built-in authentication, capabilities and gRPC service: v5 is an embeddable engine; the
  server is sigma-tkgd.
- Regional replication profiles and wall-time certification protocols.
- The handoff's capacity report: it is arithmetic with no measured inputs. v5 sizing comes
  from the gates in §5.

Assessment of the other handoff parts: three of the four TLA+ models restate their guards as
invariants; the footprint oracle restates its fixture; most acceptance cases from T14 on
have no thresholds. They are not used as evidence.

## 5. Phases

Every phase starts with failing tests, ends with a measured gate, and is scale-tested at the
three synthday sizes (790 K, 3.15 M, 12.6 M rows) from V3 on, like ADR-0011.

| Phase | Deliverables | Gate |
|---|---|---|
| **V0 Spec and oracle** | ADR-0012 (v5 semantics, decisions D1–D8 closed); Go port of the oracle; fixture runner; SEM01–16 plus the four v4 probe cases plus SOC shapes (HOP, ORIGIN, VATTR, CATTR) as fixtures | Oracle passes every fixture; owner sign-off on semantics |
| **V1 Temporal core** (pure, no I/O) | Interval maps, lives, component reducer, mutation operations, visibility evaluation | Randomized differential against the oracle (40 seeds × 80 scalar updates + 2,000 set updates, handoff `random_interval_oracle`) with zero divergence |
| **V2 Write path** | VFS, WAL, commit sequencer, OCC transactions, arena memtable, recovery | Kill at every write/fsync boundary: no acknowledged write lost under `Sync`; the v4 dirty-read and lost-update probes are impossible; ingest rate measured under `Sync` and `Buffered` |
| **V3 Storage** | Seal to segments (ADR-0011 codec + `life`, `commit_seq`, component timelines), ID directory, manifests, compaction, crash-safe manifest switch | Resident memory flat across the three synthday sizes; on-disk B/fact recorded; open time independent of data size |
| **V4 Access and indexes** | Snapshot handles, the §3.5 operations, `Declared`/`Effective`, current-state accelerator, declared indexes, statistics | Every operation equals the oracle at all retained cuts of the fixtures; scan rows/s and point-lookup latency recorded; current expansion over closed history bounded as in §3.6 |
| **V5 Consumer migration** | v4 → v5 importer; sigma-tkgd and ai-soc adapters; parity goldens | ai-soc parity golden identical; BA's largest day (22.8 M rows) ingested and queried; resources compared with v4 |
| **V6 Operations** | Change feed and WAL-shipping follower, backup/restore, retention and erasure, segment tiering to object storage | Follower byte-exact; restore reproduces a named cut; retention frees whole segments |
| **V7 Scale-out** (conditional) | Partitioning, Raft replication, cross-partition commit | Started only if V5 measurements show one node cannot meet the ingest or retention target |

Targets for V2–V5 (to be confirmed at V0 once the raw-bytes → facts conversion for ai-soc
is known): resident memory independent of history size; ingest meeting the per-day fact rate
derived from the 1 TB/day raw input; column-only scan at or above the S1 codec's measured
24 M rows/s.

## 6. The v4 line while v5 is built

- Bug fixes and releases continue on `main`. Open v4 items from the 2026-09-24 review that
  were traced but not yet verified by a test:
  - `NodesDuring` / `RelsDuring` treat an open end as wall-now + 1, missing future-only rows.
  - Update/close/delete of a row whose explicit valid-from is in the future stamp
    `TxFrom = ValidFrom + 1` without advancing the floor, a future transaction time.
  - Re-importing a deleted ID restarts at version 0 and can overwrite old history rows.
  - `SelectAsOf` (version order) and the point resolver (TxFrom, then version) can pick
    different rows after a cascade inversion.
  - `NodeMatchesValidTime` on a current row with unset valid-from accepts current properties
    for times before the last update.
  - Snowflake ID space ends 2034-12-02.
- **ADR-0011** (decision D6): recommended to stop at S1 on v4 and continue S2+ inside v5
  phase V3, because the segment format should carry `life` and `commit_seq` from the start.
  For memory relief on v4 before V5, ai-soc can run with `DisablePlannerStats` (ai-soc reads
  no statistics, ADR-0011 §4) which removes the per-relationship stat memos measured at
  2.12 GB of 8.04 GB.
- v4 receives no new features that v5 replaces.

## 7. Migration

The importer reads a v4 export stream. Each v4 entity version chain becomes lives and
component timelines; v4 `TxFrom` order becomes `CommitSeq` order, and the v4 wall-clock
stamps are kept as the commit directory's observed times, so an "as of timestamp" read gives
the same belief state as v4 where v4's answer was well defined. Cases where v4's answer
depended on the defects in §1.2 are reported by the importer, not reproduced.

## 8. Open decisions

| # | Decision | Recommendation |
|---|---|---|
| D1 | Component timelines vs whole-entity versions as the logical model | Component timelines (§3.2); bulk types collapse to one interval per row, so SOC edges pay nothing for it |
| D2 | ID scheme | 64-bit, partition tag + range-allocated sequence, no clock bits |
| D3 | Typed schema mandatory? | Mandatory for declared bulk types; other types get a typed dynamic column |
