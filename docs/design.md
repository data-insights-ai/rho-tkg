# Design Invariants

## Core Invariants

- **Pure-data structs**: Node and Relationship hold no references to Graph, registries, or resolvers. They are self-contained data containers.
- **snowflake.ID everywhere**: All entity and reference IDs are `snowflake.ID`. Customer-facing wrapper types (`types.NodeID` / `types.RelID`) are exported aliases of `snowflake.ID` so external code can pass them through but cannot reach into snowflake internals; the formerly unexported `nodeID`/`relID` aliases were renamed during the v3.4.0 cleanup.
- **Strict encapsulation**: All struct fields are unexported. Access through methods only.
- **Defensive copying**: `ExtraLabelTokens()`, `AllLabelTokens()`, `Properties()`, `DeepCopy()`, `ToMap()`, and `PropertiesMap()` always return independent copies. `PropertySlice.Set`, `Node.SetProperty`, and `Relationship.SetProperty` deep-copy accepted reference values before storing them, validate registered custom values after `DeepCopyValue`, and preserve the caller's value-vs-pointer shape.
- **Token 0 reserved**: Token 0 is invalid. `HasLabelToken(0)`, `HasTypeToken(0)`, `HasLabelTokenRaw(0)`, and `HasTypeTokenRaw(0)` always return false. Constructors keep token-0 payloads representable so callers get ordinary values; Store write validation rejects those invalid entities with `ErrInvalidStoreMutation` before persistence.
- **Extra label deduplication**: `NewNode` deduplicates extra labels and removes the primary label from extras.
- **Allowlist property validation**: `PropertySlice.Set()` recursively validates values using the exact data-plane allowlist, then stores a deep copy and validates the copied value too. Accepted built-ins are the concrete scalar types (`bool`, `int*`, `uint*`, `float*`, `string`), `[]string`, `[]int`, `[]int64`, `[]float32`, `[]float64`, `[]byte`, `[]bool`, `[]any`, `map[string]any`, and `map[string]string`; named aliases and unsupported concrete slices/maps are rejected. Registered custom struct types must satisfy the hash and deep-copy contracts. `RegisterPropertyStructType(nil)` rejects untyped nil with `ErrUnsupportedValueType`; use a zero value or typed pointer so the type is explicit. Pointers, unregistered structs, arrays, channels, functions, and unsafe pointers are rejected at any nesting depth (`ErrUnsupportedValueType`).
- **Shadow property protection**: The `tkg_` prefix is reserved. `PropertySlice.Set()` and `Delete()` reject any key starting with `tkg_`. Errors wrap `ErrReservedPrefix` for programmatic discrimination via `errors.Is`.
- **Opaque token types**: Label and relationship type tokens use unexported `labelToken` and `relTypeToken` types, preventing accidental misuse of raw `uint16` values.
- **Zero-allocation token checks**: `HasLabelTokenRaw(uint16)` on Node and `HasTypeTokenRaw(uint16)` on Relationship for graph-layer hot paths. Token 0 returns false.
- **Depth-limited validation**: Recursive validation and deep-copy stop at `maxPropertyDepth` (32). `Set()` returns `ErrMaxDepthExceeded` for deeper structures.
- **Registry input validation**: Graph-level registry token helpers reject empty, whitespace-only, and overlong names before allocation. Imported and rehydrated registry mappings are checked against the active graph `MaxNameLength` before becoming graph state. Empty strings and names beyond `MaxNameLength` are never assigned or accepted as graph tokens; no-error lookup helpers return false for malformed names.
- **Registry zero values preserve invariants**: Internal label and relationship-type registries lazily initialize the reserved token-0 entry. A zero-value registry behaves like an empty constructor-built registry: length 0, exported names `[]string{""}`, import-ready, and first allocation token 1.
- **Resolver reads are transaction-isolated**: Public no-error resolver helpers (`LookupLabel`, `LookupRelType`, node label/type resolution, and shadow-property resolution) acquire the graph read lock before reading registry pointers and return zero values once graph close is visible. Internal mutation/hash paths that already hold the graph lock use explicit lock-free helpers to avoid recursive `RLock` deadlocks.
- **Shared-pointer accessors**: `Temporal()` and `Integrity()` return the internal pointer — no defensive copy. The graph layer mutates those structs directly; `DeepCopy()` returns detached metadata when mutation isolation is needed.
- **Bulk property construction**: `NewPropertySlice(map[string]any)` is O(N log N) — allocate the result once, validate all values, deep-copy accepted reference values, and sort once. Avoids the O(N²) per-property `SetProperty` loop for entity creation.
- **Store is pure persistence**: The `Store` interface handles entity storage, index maintenance, and resource cleanup (`Close()`). Shadow resolution and string resolution live on Graph. Store node deletes fail closed rather than orphaning relationship rows: plain `DeleteNode` only removes unconnected nodes, while `DeleteNodeCascade` and `DeleteNodeWithHistory` handle connected deletes and must restore completed relationship deletes on recoverable failure. Tiered plain cascade and archive/restore final source-node removal purge stale source adjacency-only entries while deleting the node; archive/restore destination preflight purges orphan destination adjacency before writing the moving node. Badger restart rebuild uses entity rows as the liveness source for `nodeIDs` and `relIDs`; stale label/type/outgoing keys without rows are ignored, while incoming-only relationship keys remain repair-visible. Fixed-width Badger scans require exact key lengths before parsing IDs, so overlong prefixed keys cannot be truncated into live state. Badger orphan cleanup, tiered relationship routing, and repair shard probes check the relationship row itself. Repair removes the complete local orphan relationship index set, not just the incoming key that exposed it. Three implementations: `memory.Store` (in-memory; zero value is usable), `badger.Store` (persistent), `tiered.Store` (multi-shard).
- **Explicit adjacency targets are validated**: Outgoing/incoming relationship reads are explicit-node APIs. A missing requested node returns `ErrNodeNotFound`; an existing node with no matching relationships returns an empty result. Batched `ForNodes` reads are all-or-error and must not return partial maps when any requested node is absent.
- **Temporal neighbor reads separate temporal existence from current adjacency**: `g.Temporal.NeighborsAt` must validate the target node with `NodeAt` semantics for the queried instant, then treat `ErrNodeNotFound` from current adjacency indexes as an empty current candidate set so deleted-but-historical target nodes can still use relationship history.
- **Configured Store is validated**: omitting `Config.Store` selects the default backend path, but a typed nil Store interface is rejected by `graph.New` with `ErrNilStore` before the graph is constructed. Nil concrete in-tree Store receivers return the same sentinel from lifecycle `Close` and `Clear` calls instead of panicking.
- **Store index targets use real labels and properties**: Direct Store property, temporal, high-frequency, and vector index APIs reject label token 0 with `ErrInvalidStoreMutation`. Property/vector index targets plus graph-level stored-property queries (`NodesByLabelAndProperty`, `NodesByLabelProperty*`, `RelsByTypeProperty*`) reject reserved `tkg_` keys with `types.ErrReservedPrefix`. Persisted Badger/Tiered index definitions are checked on open, and Tiered vector definition files reject conflicting duplicate `(label, property)` records.
- **In-flight index creates are not durable definitions**: Badger property, temporal, high-frequency, and vector definition writers plus Tiered vector definition writers skip phased-create placeholders until finalization completes. Placeholder visibility is for concurrent maintenance only.
- **In-flight index creates are not query sources**: Badger property, temporal, and high-frequency query fast paths ignore building placeholders and fall back to complete scans. Badger/Tiered vector search returns `ErrVectorIndexNotFound` while a vector placeholder is still backfilling.
- **No-error index helpers tolerate nil and zero values**: Internal property indexes initialize value maps on first `Add`; zero-value high-frequency indexes initialize bucket maps on first `Add`; zero-value LRU caches lazily initialize as minimum-capacity caches; nil property, temporal, high-frequency, and vector cleanup/read helper receivers no-op or return zero/nil values. Nil vector writes/searches have an error channel and return `ErrInvalidVectorIndexConfig`.
- **Store iteration callbacks are validated**: Memory, Badger, and Tiered `ForEach*ID` APIs return `ErrInvalidStoreMutation` for nil callbacks on open stores instead of panicking inside backend locks or shard callbacks. Closed stores still return `ErrStoreClosed` first.
- **Store registry pointers are validated**: Badger and Tiered registry save/load APIs return `ErrInvalidStoreMutation` for nil label or relationship-type registries on open stores. Closed stores still return `ErrStoreClosed` first. `tiered.Store.SetLabelRegistry(nil)` is a no-op.
- **Tiered migration owns source registries**: `MigrateFromBadger(src, dst)` requires an empty destination, loads label and relationship-type registries from the source BadgerStore, preflights migrated entity tokens and relationship endpoints against source data, wires destination ontology from the label registry, and saves both registries to the destination after a successful copy. Failures roll back inserted destination entities, restore the previous ontology registry, and restore or remove the destination registry file to match its pre-migration state. Nil stores, non-empty destinations, and missing source registry metadata for non-empty data return `ErrInvalidStoreMutation`; closed stores return `ErrStoreClosed` before any empty migration can report success.
- **Temporal constraint iteration validates callbacks**: `ConstraintSet.ForEach(nil)` returns `ErrInvalidTemporalConstraint` before inspecting set length, so empty and non-empty sets share one invalid-input contract.
- **Temporal constraint registration validates kinds**: `g.Constraints.Add` and `Set` reject unknown `TemporalConstraint.Kind` values before changing the graph's constraint set. Invalid configuration must fail at the public boundary, not wait until a later relationship write.
- **Context and transaction callbacks are validated**: Public graph context helpers return `ErrNilContext` for nil contexts before selecting on `ctx.Done`; `g.Tx.Run` and `RunContext` return `ErrNilTxCallback` for nil callbacks before opening a transaction.
- **Graph façade and sub-API nil receivers fail closed**: nil, zero-value, or typed-nil `*Graph`, `TxAPI`, `BatchAPI`, and public sub-API wrappers with error returns return `ErrNilGraph` instead of panicking on nil internals. No-error helpers return zero values.
- **Entity nil receivers fail closed**: nil `*types.Node` and `*types.Relationship` accessors return zero values, no-error mutators no-op, and error-returning mutators return `ErrNilNode`/`ErrNilRelationship`. Nil `*PropertySlice` pointer mutators return `ErrNilPropertySlice`; nil `*types.TemporalMetadata` helpers and nil integrity `DeepCopy` calls also return zero/nil without panicking.
- **IO stream endpoints are validated**: `g.IO.Export` and `tx.Export` return `ErrNilWriter` for nil or typed nil writers; `g.IO.Import` and `ImportWithOptions` return `ErrNilReader` for nil or typed nil readers before staging files or stream writes are attempted.
- **Provider extension inputs and lifecycle are bounded**: `g.Index.RegisterProvider` and `RegisterLegacyProvider` reject nil and typed nil providers before calling `Name()`, and provider registration/unregistration rejects empty or whitespace-only names before registry mutation or lookup. `g.Index.Providers()` checks the closed flag under the graph read lock and returns an empty list once graph close is visible because it has no error return. `Graph.Close()` and `g.Index.UnregisterProvider` wait for any in-flight provider `Init` before calling provider `Close()`.
- **Memory close state is authoritative**: After `memory.Store.Close`, public error-returning APIs return `ErrStoreClosed` before reading or mutating process-local maps, including empty fast paths. Exported test-only tampering helpers return no data or no-op after close.
- **Memory zero value is initialized lazily**: A zero-value `memory.Store` behaves as an empty store. Reads return not-found/empty results, and writes, indexes, and history paths initialize maps at the lifecycle gate before mutation.
- **Persistent zero values fail closed**: Zero-value `badger.Store` and `tiered.Store` values are not operational backends, but lifecycle and checked read/write entry points return `ErrStoreClosed` instead of panicking on nil internal database, channel, or shard handles.
- **Badger close state is authoritative**: After `badger.Store.Close`, public error-returning APIs return `ErrStoreClosed` before cache/index/count/history fast paths can report stale state. Public no-error diagnostics and routing helpers return zero or nil after close. The private `flush()` path still returns the Badger closed-DB sentinel for the low-level WriteBatch deadlock guard.
- **Vector search scans re-check lifecycle and apply QueryOpts before rank loss**: In-tree Store vector searches release some Store-level locks while scanning vector entries and invoking eligibility filters. They must re-check close state after the scan/filter phase and before returning empty or raw-ID results. Direct Store `SearchNearestNodes` must apply temporal/depth eligibility before heap selection and `QueryOpts.After`/`Limit` over the distance-ranked slice; graph-level search must pass only backend-relevant opts, cap temporal over-fetch result buffers by the bounded probe ceiling, and paginate the resolved result once.
- **Temporal pages limit after exact eligibility**: Store queries that accept temporal `QueryOpts` must consume `Limit` only after temporal metadata has been checked. Badger cache-miss candidates from index snapshots are unknown, not eligible; apply the cursor first, fetch the row, then count it toward the page only if it matches.
- **Query option and target validation precede empty shortcuts**: graph-level query APIs validate `QueryOpts.Depth`, `QueryOpts.Limit`, `QueryOpts.After`, and active temporal interval ranges before label/type/index existence checks and non-positive-k vector shortcuts. `g.Index.SearchNearest` also validates malformed label/property targets and unknown labels before the `k <= 0` empty result. Temporal label and label+property helpers reject malformed labels/types before unregistered-target empty results. Invalid options and malformed targets are errors even when the queried namespace is empty or the requested result count is non-positive.
- **Query limits are non-negative**: `QueryOpts.Limit` accepts `0` for unbounded queries or a positive maximum. Negative limits return `ErrInvalidQueryLimit`; they must never be treated as unbounded.
- **Query cursors are non-negative**: `QueryOpts.After` accepts `0` for the first page or a non-negative entity cursor. Negative cursors return `ErrInvalidQueryCursor`; they must never be treated as the first page.
- **Raw history cursors share the same pagination contract**: `AllNodeHistoryIDsFrom` and `AllRelHistoryIDsFrom` also reject negative limits with `ErrInvalidQueryLimit` and negative cursors with `ErrInvalidQueryCursor` before empty-history shortcuts.
- **History retention is non-negative**: `TruncateNodeHistory` and `TruncateRelHistory` reserve `keepVersions == 0` for explicit clear-all; negative retention returns `ErrInvalidStoreMutation` and must not delete history.
- **Persisted entity IDs are positive**: graph import-by-ID APIs reject negative caller-supplied IDs with `ErrInvalidID`; graph update, label mutation, property CAS, close-version, delete, admin archive/restore, and tx/batch variants reject zero or negative target IDs with `ErrInvalidStoreMutation` before lookup, snapshot, capability checks, or queueing; graph relationship create/import paths reject zero or negative endpoint IDs before endpoint work; Store current-row, history snapshot, relationship index, delete/cascade, archive/restore, and batch write/delete mutations reject zero or negative entity IDs with `ErrInvalidStoreMutation` before mutation.
- **Import staging caps are non-negative**: `ImportOptions.MaxStagedBytes == 0` is unlimited, positive values cap the staging file, and negative values return `ErrImportSizeLimit` before creating a staging file.
- **Entity versions never wrap**: versioned mutations use a checked next-version helper. A current `math.MaxUint32` version returns `ErrVersionOverflow` before history writes, wrapped version `0`, or label-token allocation for rejected add-label calls. Version-chain successor lookup returns no successor for `math.MaxUint32`; it must not wrap to genesis version `0`. Version-chain navigation must also validate explicit IDs so unknown nodes/relationships return `ErrNodeNotFound`/`ErrRelNotFound`, not `nil, nil`.
- **Interval QueryOpts require valid active ranges**: `ValidStart`/`ValidEnd` activate interval filtering only when both bounds are greater than zero, and active intervals require `ValidStart < ValidEnd`. Core and Store predicates must share that rule so graph-level history resolution does not diverge from Store pushdown.
- **Query target names validate before lookup**: graph-level label/type query and count APIs reject empty, whitespace-only, or overlong names before registry lookup. Adjacency helpers reserve empty `typeName` for "all types" and validate every non-empty type filter.
- **Mutation target names validate before unrelated work**: node label mutations and relationship type creation reject empty, whitespace-only, or overlong names before property validation, entity lookup, registry lookup, transaction snapshots, ID generation, or store writes.
- **Update maps validate before snapshots and queueing**: standalone, transaction, and batch update paths share update-map validation. Transactions reject malformed keys/values before rollback snapshot lookup; batch queues accept provenance/authorization shadow keys and reject other `tkg_` keys before enqueueing.
- **Batch update queues own their inputs**: after validation, queued update maps are deep-copied, including nested property values and provenance signatures. Caller mutations after queueing must not affect `Execute`.
- **Batch empty updates are read-only no-ops**: `BatchBuilder.Execute` checks existence for queued empty updates, records failures for missing entities, but does not increment `Updated` or publish update events when the read succeeds.
- **Batch create stats mirror batch results**: successful batch node and relationship creates must increment `NodesAdded`/`RelsAdded` in `g.Stats.Get()` in the same units as the create contribution to `BatchResult.Created`.
- **Batch event buffers flush atomically**: `BatchBuilder.Execute` must publish buffered mutation events with one `Publisher.PublishBatch` call after graph and builder locks are released. Per-event `Publish` loops let async dispatch observe only a prefix of the batch and break priority ordering.
- **Event bus setters report lifecycle errors**: `g.Events.SetSync` and `SetAsync` must return `ErrGraphClosed` after graph close and leave the installed publisher unchanged. Public graph-owned state mutators should not silently no-op when an error can be returned.
- **Temporal close stats mirror update events**: successful `CloseVersion` calls persist entity state, publish update events, and must increment `NodesUpdated`/`RelsUpdated`; rejected no-op close attempts must not.
- **Rollback restores stats visibility**: `GraphTx.Rollback` must restore the operation-counter snapshot from `BeginTx` after a successful rollback so uncommitted transaction writes do not appear in `g.Stats.Get()`.
- **Rollback snapshot keys include entity kind**: transaction rollback must key first-mutation snapshots by node-vs-relationship identity as well as snowflake ID. `types.NodeID` and `types.RelID` are distinct API identities even when caller-supplied imports use the same underlying value.
- **Registries mutate only after rejecting validation passes**: add-label paths must check idempotence, node existence, and `MaxLabelsPerNode` before creating a new label token. Node create/import/add-label final write failures restore newly allocated labels. A failed mutation must not leave unreachable registry names behind.
- **Batch node labels allocate at execute time**: `BatchBuilder.AddNode` must not register unseen labels while queueing. Queue-time nodes use non-zero probe tokens; `Execute` allocates real label tokens, retokenizes returned pointers in place, and rolls labels back if persistence fails or panics.
- **Batch relationship state restores on failed create**: execute-time relationship fields (`TxFrom`, endpoint hashes, and real type token) must return to queue-time values when endpoint refresh, constraints, type allocation, or the final Store write rejects a batch relationship create.
- **By-ID relationship state matches object-form creation**: `AddByID` and `AddByIDIfAbsent` use endpoint IDs as input, but still fetch live endpoints under endpoint locks, capture endpoint hashes, enforce constraints, and allocate relationship-type tokens only after endpoint fetches succeed.
- **Rel-type tokens follow rejection checks**: direct, import, and batch relationship create paths run endpoint and temporal-constraint rejection paths before allocating a token for a previously unseen relationship type. If the final store write fails after allocation, restore the pre-allocation registry snapshot. Failed writes must not leave unreachable type names behind.
- **Registry rollback windows are panic-safe**: any path holding the graph registry allocation mutex across a backend call must release it via `defer`, including panic unwinds from custom Store implementations. Multi-label allocation helpers also restore partial suffixes when a later label fails before the backend call begins.
- **Index label tokens roll back on backend create failure**: graph-level index create APIs may create a label token so a successful index applies to future nodes, but if the backend create call fails, restore the pre-allocation label registry snapshot.
- **Badger delete lock scope**: Badger node/relationship deletes prefetch cache-miss rows before taking `idxMu.Lock`, then re-read the current cached row under the write lock so index cleanup uses the row actually being deleted.
- **Badger SyncWrites covers metadata and split keys**: property, temporal, high-frequency, and vector index create/drop paths enqueue persisted definition updates and then flush after `idxMu` is released when `SyncWrites` is enabled. Badger split relationship helpers flush their queued entity/out and incoming-index writeOps too.
- **Tiered vector definition files are all-or-error**: `CreateVectorIndex` and `DropVectorIndex` snapshot the raw persisted definition file before writing, restore or remove it on write failure, and fsync the metadata directory after deleting the last vector-index definition.
- **Tiered temporal definition files are all-or-error**: temporal and high-frequency index create/drop snapshot the raw persisted tracking file before writing, restore or remove it on write failure, and keep shard-local rollback tied to metadata persistence.
- **Tiered catalog files are all-or-error**: `ShardCatalog.Save` snapshots the raw JSON file before writing and restores or removes it on write failure so in-memory catalog rollback cannot diverge from the persisted catalog.
- **Tiered registry files are all-or-error**: the flat `registry.msgpack` save helper snapshots the raw file before writing and restores or removes it on failure so direct registry saves do not change durable metadata after returning an error.
- **Tiered registry files validate on load**: `registry.msgpack` load rejects malformed label or relationship-type slices before returning metadata to startup/load code or deprecated single-registry save paths.
- **Tiered rotation inherits indexes before committing topology**: hot-shard rotation installs tracked temporal and high-frequency indexes on the newly opened shard before catalog or live topology changes. Setup failure closes/removes the new shard and leaves the old hot shard active.
- **Tracked index application is rollback-safe**: applying store-level temporal/HFI tracking to a single Badger shard must roll back indexes created earlier in that apply call if a later tracked definition conflicts or fails. Persisted tracking load must also roll back earlier shard creations if a later shard fails. Lazy archive open and hot-shard setup must not leave a partially applied target shard after returning an error.
- **Tiered temporal index kind is uniform across shards**: a label may use either the interval temporal index or the high-frequency index, never a mix. HFI bucket sizes must be positive whole milliseconds so bucket math matches `Instant` precision, and same-kind HFI retries must use the same bucket size. Tiered create paths allow same-kind retries after partial success, reject cross-kind or different-bucket HFI shard leftovers with `ErrTemporalIndexExists` before adding indexes to other shards, and roll back earlier shard-local changes if a later shard fails during create or drop.
- **High-frequency indexes are real secondary indexes**: Store-level HFI creation must backfill matching current nodes and node mutation paths must keep HFI buckets in sync after creation. Badger HFI creation uses a visible placeholder while backfilling; corrupt existing rows fail creation and remove only that placeholder so tiered callers can roll back earlier shard creates.
- **`tiered.Store` shard routing**: Reference entities go to `refShard`; graph-generated current event entities go to the hot time-windowed event shard, while caller-supplied/backfilled event node IDs go to the shard selected by their snowflake timestamp. Public Store duplicate checks include closed cold shard owners before accepting caller-supplied IDs; relationship duplicate checks resolve actual owner placement, not only the relationship ID timestamp, because a current-ID relationship can still be stored on an old start-node shard. Core-generated fresh IDs use an internal generated-ID fast path, including batch node execution, to keep the normal create path from opening unrelated cold shards. Weekly windows use ISO week starts, and accepted sub-day windows use fixed-duration starts that contain the timestamp; `ShardWindow` must be at least 1 minute and a whole millisecond. Persisted shard catalogs reject duplicate names, multiple hot event shards, invalid kind/tier combinations, unsafe paths, negative stats, and invalid event windows before reopening shards. Shard resolution for existing entities is O(1) via `shardForNodeID` (ref probe + snowflake timestamp extraction). Cross-shard relationships use split writes: entity+out/ in start shard, in/ in end shard. `shardForRelIDChecked` probes all event shards for cross-shard entities. Merge queries use parallel goroutines per shard. `Store.Close` and `closeIdleShards` synchronize on each event shard mutex before closing or clearing the shard handle. Checked routing, create-time rotation, valid index create/drop/search calls, direct read/count/bulk/history APIs, empty batch/history write edges, and public admin/metadata operations fail with `ErrStoreClosed` after close starts.
- **Update operations**: `UpdateNode(id, updates)` / `UpdateRelationship(id, updates)` perform read-modify-write under entity lock. Property keys with `nil` values are deleted; non-nil values are set/overwritten. Each update bumps the version counter and sets `temporal.UpdatedAt`. Empty updates map is a no-op (no lock, no version bump). Update paths extract provenance/authorization shadow keys, reject other `tkg_` keys, and validate values (`ValidatePropertyValue`) before acquiring the lock or taking transaction snapshots. Update-style paths, including node property CAS, recheck `MaxPropertiesPerEntity` after applying the final add/delete/set shape and before persistence.
- **Metadata-blind rehash preservation**: APIs that recompute `Hash`/`PrevHash` without accepting provenance shadow keys (`CloseVersion`, node label add/remove, node property CAS, in-place updates) must preserve existing provenance, signature, authorization, and relationship endpoint-hash fields on the integrity struct.
- **Replace vs Put semantics**: `ReplaceNode`/`ReplaceRelationship` (Store interface) require existence — return `ErrNodeNotFound`/`ErrRelNotFound` if missing. `PutNode`/`PutRelationship` reject duplicates — return `ErrNodeExists`/`ErrRelExists` if present. Put, replace, batch, and split relationship helper writes/deletes reject zero or negative entity IDs, zero node-label tokens, zero relationship type/endpoints, and nil replacement/history payloads with `ErrInvalidStoreMutation` before mutating state. Replace overwrites entity data only; labels and relationship type/endpoints are immutable after creation — no index changes. Node Store replacements and history replacements reject label-token changes with `ErrInvalidStoreMutation`. Dedicated node label-token helpers accept only exact one-token additions/removals before touching label indexes or history. Relationship Store replacements, history replacements, and tombstones reject type/endpoint changes with `ErrInvalidStoreMutation`.
- **Transaction label rollback preserves indexed identity**: `GraphTx.Rollback` restores multi-step node label mutations by comparing the current label sequence with the pre-transaction snapshot and applying exact one-token Store label writes until the target sequence is live. Only then can replacement restore the rest of the node row without violating Store replacement invariants or leaving label indexes stale.
- **Cascade-delete on node removal**: `g.Nodes.Delete` (post-v3.4.0; was `Graph.DeleteNode` pre-thin-facade) removes all outgoing and incoming relationships before the node. Self-loops are handled by skipping `ErrRelNotFound` in the incoming pass. The graph layer re-reads the node and relationships under the final `LockMany` before building tombstones, so delete history reflects the locked current rows. The tombstone history entries for all cascaded relationships and the node itself are written atomically in a single store call (`DeleteNodeWithHistory`) — no orphaned history entries on crash. Plain Store `DeleteNode` and `DeleteNodesBatch` reject connected nodes with `ErrInvalidStoreMutation`; `DeleteNodeWithHistory` validates that supplied tombstones cover every live connected relationship and no unrelated or duplicate relationship tombstones before mutating. Tiered plain cascade, node batch, and relationship batch deletes keep preflight snapshots so earlier accepted relationship or shard deletes can be restored if a later shard or split-delete fails; tiered plain cascade also purges stale adjacency-only entries during final shard-local node removal, and archive/restore destination preflight purges orphan adjacency-only entries for the moving node.
- **SnowflakeID bridges**: `NodeID.SnowflakeID()`, `RelID.SnowflakeID()`, `EntityID.SnowflakeID()` — exported methods on the customer-facing `types.NodeID` / `types.RelID` / `types.EntityID` wrapper types allow cross-package persistence key extraction without leaking the `snowflake.ID` dependency into entity method signatures. (Pre-v3.4.0 these wrappers were unexported; the rename moved the bridge methods to the exported types without changing their callable shape.)
- **Shadow resolution nil-guards**: `ResolveNodeProperty` / `ResolveRelProperty` check `Temporal() != nil` and `Integrity() != nil` before accessing fields. New entities without metadata return `(nil, false)` instead of panicking.

## Shadow Properties (21)

Read-only virtual properties managed by the graph layer:

| Key | Type | Applies To |
|-----|------|------------|
| `tkg_labels` | `[]string` | Node |
| `tkg_type` | `string` | Relationship |
| `tkg_valid_from`, `tkg_valid_to` | `Instant` | Both |
| `tkg_tx_from`, `tkg_tx_to` | `Instant` | Both |
| `tkg_created_at`, `tkg_updated_at`, `tkg_deleted_at` | `Instant` | Both |
| `tkg_created_by`, `tkg_updated_by` | `string` | Both |
| `tkg_version` | `uint32` | Both |
| `tkg_hash`, `tkg_prev_hash` | `string` | Both |
| `tkg_base_entity` | `entityID` | Both |
| `tkg_from_hash`, `tkg_to_hash` | `string` | Relationship only |
| `tkg_author_id` | `string` | Both |
| `tkg_signature` | `[]byte` | Both |
| `tkg_authorized_by` | `string` | Both |
| `tkg_auth_level` | `uint8` | Both |

`tkg_author_id`, `tkg_signature`, `tkg_authorized_by`, and `tkg_auth_level` are write-path shadow keys: pass them in the `props`/`updates` map of any Add or Update call to store provenance/authorization on the integrity struct. They are stripped before `PropertySlice` construction (never stored as real properties) and readable back via `ResolveNodeProperty` / `ResolveRelProperty`. `tkg_auth_level` accepts signed/unsigned integer values and whole-number `float32`/`float64` values in `[0, 255]`; out-of-range, fractional, or non-numeric values return an error.

`tkg_valid_from`, `tkg_valid_to`, and `tkg_created_at` are write-path temporal shadow keys: pass them in Add props to populate `TemporalMetadata` directly. They accept `types.Instant`, signed integer milliseconds, unsigned integer milliseconds that fit in `int64`, and whole-number `float32`/`float64` milliseconds inside each float type's contiguous exact integer range.
